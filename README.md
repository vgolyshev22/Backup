Задание 1. Резервное копирование


Кейс

Финансовая компания решила увеличить надёжность работы баз данных и их резервного копирования.


Необходимо описать, какие варианты резервного копирования подходят в случаях:


1.1. Необходимо восстанавливать данные в полном объёме за предыдущий день.
В данном случае подойдет полное резервное копирование (Full Backup).

Например, можно настроить создание полной резервной копии базы один раз в сутки ночью. В резервную копию попадет вся база данных на момент выполнения бэкапа.

Если на следующий день произойдет сбой, мы сможем взять последнюю созданную резервную копию и восстановить базу в том состоянии, в котором она находилась на момент создания бэкапа.

Плюс такого способа в том, что восстановление достаточно простое, так как для него нужна одна полная резервная копия.

Минус — полный бэкап занимает больше места и его создание сильнее нагружает систему, чем создание инкрементных копий.

1.2. Необходимо восстанавливать данные за час до предполагаемой поломки.
В данном случае одного полного бэкапа раз в сутки уже будет недостаточно.

Можно использовать комбинацию полного и инкрементного резервного копирования.

Например:

00:00 — полный бэкап
01:00 — инкрементный бэкап
02:00 — инкрементный бэкап
03:00 — инкрементный бэкап
...

Полный бэкап содержит всю базу, а каждый следующий инкрементный бэкап содержит изменения, которые произошли после предыдущего резервного копирования.

Если база сломалась, например, в 15:30, можно восстановить полный бэкап, а затем применить к нему инкрементные копии до 14:00.

Таким образом, база будет восстановлена примерно до состояния за час до поломки.

Задание 2. PostgreSQL


2.1. С помощью официальной документации приведите пример команды резервирования данных и восстановления БД (pgdump/pgrestore).
Для создания резервной копии PostgreSQL можно использовать утилиту pg_dump.

Например, есть база test_db. Создадим ее резервную копию:

pg_dump -Fc test_db > test_db.dump

Здесь:

pg_dump — утилита создания резервной копии PostgreSQL;
-Fc — создание бэкапа в формате custom;
test_db — база, которую необходимо сохранить;
test_db.dump — файл с резервной копией.

Формат custom удобен тем, что такой бэкап можно восстанавливать с помощью pg_restore.

Для восстановления сначала создадим пустую базу:

createdb test_db_restore

После этого восстановим в нее данные:

pg_restore -d test_db_restore test_db.dump

Здесь:

pg_restore — утилита восстановления;
-d test_db_restore — база, в которую необходимо восстановить данные;
test_db.dump — созданная ранее резервная копия.

То есть в результате содержимое test_db.dump будет восстановлено в базу test_db_restore. Такой способ создания и восстановления резервной копии соответствует варианту из официальной документации PostgreSQL.

Задание 3. MySQL

3.1. С помощью официальной документации приведите пример команды инкрементного резервного копирования базы данных MySQL.
В MySQL для инкрементного резервного копирования можно использовать binary log (binlog).

В binary log записываются изменения, которые происходят с данными в базе. За счет этого после создания полного бэкапа можно сохранять уже не всю базу заново, а изменения, произошедшие после него.

Сначала необходимо убедиться, что binary log включен. Посмотреть существующие binary log можно командой:

SHOW BINARY LOGS;

Допустим, ранее был сделан полный бэкап, после которого MySQL записывал изменения в binary log.

Для переключения на новый binary log можно выполнить:

FLUSH LOGS;

После выполнения этой команды текущий binlog закрывается и MySQL начинает записывать изменения в новый файл.

Предыдущие binary log можно скопировать в место хранения резервных копий. Именно они будут содержать изменения, которые произошли после предыдущего полного или инкрементного бэкапа. Такой принцип инкрементного резервного копирования описан в официальной документации MySQL.

Для восстановления сначала используется полный бэкап базы, после чего с помощью mysqlbinlog можно применить сохраненные изменения:

mysqlbinlog mysql-bin.000001 mysql-bin.000002 | mysql -u root -p

В результате сначала восстанавливается состояние базы из полного бэкапа, а затем к нему применяются изменения из binary log.
